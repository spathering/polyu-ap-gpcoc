## 项目目标

试实现一个用于线上多人跑团的通用工具，并探索相关的技术与协作方案。

## 当前阶段

项目处于原型验证阶段，已建立文档分类、索引和维护标准；当前文档进一步区分设计与工程，工程目录和施工占用统一在 hierarchy 中维护。

本机首测工程已建立，采用 Python 3.14 / Lua 5.4，提供主机权威后端、独立文件存储、本机联机、动态规则、持久流程与聊天室后端。实际能力与限制见 [工程说明](../engineering/first-test.md) 和 [验收报告](../engineering/first-test-acceptance.md)。原 Lua 同步内存实验仍保留，完整线上跑团产品尚未完成。

## 已确认的技术决策

2026-10-29，用户确认现阶段自定义规则与自定义流程统一使用 **Lua**，以运行时读取加载脚本文件和游玩中临场新增规则为需求背景。该决定替代此前 JS/Lua 并列选型的安排；不同时确定后端实现语言，也不表示动态加载、版本切换和流程恢复已经实现或验证。

Lua 首测宿主已实现短业务调用、隔离工作进程、动态导入、不可变修订、持久回执和阶段等待恢复。当前写法见 [Lua 编写说明](../engineering/lua-authoring.md)；更广泛的扩展需求保留在计划中。

2026-10-30，用户确认**数据管理抽离为独立模块，首个测试版先实现并使用基于文件的管理模块**；数据库是否引入留待后续需求评估。该决定替代首测工程草案中的 SQLite 建议。本次首测已经实现 FileDataStore，账号与房间分开保存，具体提交/恢复边界见 [工程说明](../engineering/first-test.md#4-数据与文件提交)。

## 房间与规则的数据设计决策

2026-10-30，用户确认以下设计方向，作为后续实现约束：

- 房间是跨多日的长期存档单位。房间始终以主机数据为权威，全部游戏计算在主机进行，所有参与者共享同一剧情进度。
- 个人进度指事件在对应玩家或角色上的解锁、触发、知情及待办记录，附于各自相关容器，由主机保存与恢复，不产生玩家独立推进的世界副本。
- 数值表保存原始数值与当前持久状态；组合数值在需要使用或显示时调用主机规则计算。只读计算与产生业务效果的行动流程分开，规则可引用其他规则，须避免调用成环，并由流程配置明确应用顺序。
- 持有、装备、技能归属、状态承受和来源通过带类型的引用关系表达，关系可附标签或元数据；对象标签与数值分类各归相应数据定义。
- 规则容器保存规则引用，实例属性和参数由既有数值/引用容器及执行上下文提供；配置级行为定义把攻击、闪避、入场等事件映射到入口流程。

以上决策已有首测实现子集；具体状态效果和回合业务由游戏需求与规则包继续扩展。通用结构讨论见[数据与容器方案第 3.3—3.8 节](<../../plans/project planning/data-container-model.md#33-房间存档运行场次与连接生命周期>)，待实施内容继续在计划中维护。

## 通用能力与游戏包边界

2026-10-30，用户进一步确认：

- 完整 COC 规则及其他具体游戏规则归配置包实现；平台提供数据、规则执行、流程、权限与通信基础，不把完整 COC 作为宿主内置规则。
- 聊天室属于本阶段的通用后端能力，已完成结构整理和实现，见 [聊天室后端](../engineering/chat-backend.md)。聊天消息、行动审计与数据变化日志保持不同语义；聊天文字本身不能替代主机计算结果。
- 线上桌游场景主要以逻辑图表达，部分游戏可能需要 2D 或 3D 空间。地图、逻辑图编辑、空间计算、地图战斗均暂不作为必要能力纳入实现。后续按具体游戏需求确定扩展，不以当前缺少地图功能判断通用后端未完成。
