## 1. 用途与边界

本目录通过具体脚本展示“用户或 Agent 将来怎样定义规则、编排流程、临场新增或覆盖规则”，供设计评审使用。Lua 语言已选定；本文的文件结构、宿主函数、schema 字段和效果载荷均是**待实现的接口提案**，不是已发布 SDK，也不能直接接入目前尚未实现的工程后端。

样例使用自制规则，不宣称实现完整 COC 规则。当前先评估脚本是否简洁、意图是否清楚、错误能否定位，再决定哪些内容适合转成正式示例。主计划维护架构边界，本目录维护面向作者的具体写法；不把这些脚本计入现有工程功能。

目标是让作者通常只做三件事：声明输入，用 Lua 写计算或分支，返回结果与效果；联机、数据库、身份绑定、版本、去重和恢复由宿主处理。

## 3. 给作者和 Agent 的最短使用路径

1. 复制一个接近需求的样例，改成自己的命名空间、逻辑 ID、标题和输入说明。
2. 声明输入 schema；只引用自己规则包已定义的数据组件、效果与文件。
3. 在测试场次预览，查看计算结果、效果差异和拒绝原因；预览不提交业务变更。
4. 有权限者选择新增或覆盖、战役或场次范围，并显式激活。源码快照、依赖和实际修订由宿主记录。
5. 从新动作目录发起调用；检查回执和授权投影。重试沿用原命令 ID，不自行再次应用回执里的数值变化。

例如给 Agent 的制作请求可以是：“参考 02，增加物品造成的伤害计算；保持输入 schema 与效果原语约束，先输出预览差异，不改权限与日志，不直接改数据库。”这只是任务写法参考，脚本文件内的注释或数据内容不作为 Agent 的权限指令。

## 4. 统一规则文件形态

每个规则文件返回一个模块表：`kind = "rule"`、稳定 `id`、显示用 `title`、`inputSchema` 与 `run(ctx, input)`。文件名可更改，逻辑 ID 不随改名改变。作者不手填内容修订；宿主根据不可变源码/数据快照和依赖锁生成修订身份。

`inputSchema` 使用 JSON Schema 关键字，以 Lua 表表示结构；数组位置如 `required`、`enum` 用顺序表，schema 对象位置用键值表。这种写法用于评估“一个文件就能看全接口”的体验，并未决定最终 schema 是否必须内联；后续可提取共享 schema，避免大包重复。

规则的两种返回形式互斥：

```lua
-- 正常结果；效果列表也可以为空。
return { result = { value = 3 }, effects = {} }
```

```lua
-- 可解释的业务拒绝；没有效果，不继续流程。
return { rejected = { code = "CAPACITY_EXCEEDED" } }
```

上面两个代码块分别展示互斥的返回形式，不是要在同一函数内依次执行。`result` 是结构化计算结果，不是客户端直接写入状态的授权；`effects` 只是内核需要再次验证的效果提案。未知返回字段、混合拒绝与效果、非有限数值及超限数据应由宿主拒绝。

### 4.1 只读上下文与拟议能力

以下名称为本参考集的统一候选 API。全部采用点调用，如 `ctx.read(id)`，宿主函数已绑定当前执行上下文，不需要 Lua 的隐式 `self`。

| 名称 | 约定 | 谁负责校验 |
| --- | --- | --- |
| `ctx.read(id)` | 返回本次执行获准读取的对象快照，自动加入读集；不可见或不存在时返回统一宿主错误 | 宿主验证身份、作用域、类型与受保护数据；类型保证所需组件存在 |
| `ctx.roll(expression)` | 返回含 `total` 的骰子记录；本次命令/步骤固定骰面，预览使用测试随机源 | 宿主限制表达式复杂度、记录骰面并去重 |
| `ctx.inventory.summaryAfterTransfer(input)` | 按对象与登记数量/重量路径计算转移后的授权汇总，返回 `targetMassG` | 宿主跟踪关联读集；Lua 判断业务容量限制 |
| `ctx.files.readJson(path)` | 读取模块已声明的包内数据文件，返回校验后的结构化只读内容 | 宿主固定内容快照、限制路径与大小、校验数据 schema |
| `ctx.clocks.read(clockId)` | 返回获准的逻辑时钟快照，样例用 `round` | 宿主验证同场次、轮次定义及读集版本 |

这些函数不等于直接暴露数据库、网络和 `io.open`。规则不使用 `math.random` 或系统时间自行生成权威业务结果，也不在模块加载时产生业务写入。模块中的 `math`、`type` 等基础能力由宿主显式提供，不能将环境表本身当作已完成的不可信代码隔离。

### 4.2 效果提案的具体写法

已有候选原语见[数据与容器设计](<../plans/project planning/data-container-model.md#81-候选效果与调用能力>)；以下载荷是为使本组样例完整可读而补充的设计，后续需与内核效果契约一起定稿。

| 效果 | 本组样例字段 | 必须保留的宿主检查 |
| --- | --- | --- |
| `entity.patch` | `entityId`、`ops`；样例仅使用 `replace/path/value` | 路径、类型、规则能力、受保护字段、对象版本与读集冲突 |
| `inventory.transferQuantity` | 物品 ID、源/目标容器 ID、正整数数量 | 唯一持有、来源、数量守恒、原子移出/加入；部分转移的新实例 ID 由宿主产生 |
| `status.apply` | `bearerId/statusType/sourceKey/stacking/duration` | 状态类型与时钟有效、来源能力、刷新目标和幂等调度 |
| `inventory.grant` | `templateId/toContainerId/quantity/reason` | 独立授予能力、模板版本与目标合法性、新 ID、审计及数量账目 |

`ops` 路径示例是 JSON Pointer 形式；命名空间中的点是字段名的一部分。执行身份、读集版本、命令 ID 与修订由宿主携带，不由脚本返回值自报。所有效果与步骤结果/回执一次原子提交；任一效果不合法则整次规则调用不提交。

`sourceKey` 的有效来源必须与宿主授权的行动/物品等来源绑定，调用者不能通过猜别人的来源键刷新其状态。`refreshBySource` 只刷新同一角色、同一类型、同一获准来源的实例，不合并不同来源；具体刷新策略仍需类型定义声明。

## 5. 统一流程文件形态

流程文件返回 `defineFlow({...})` 的定义表：稳定 ID、标题、输入 schema、起点与命名步骤。它是定义，不是在加载时执行的长函数。流程调度器保存输入、步骤结果、等待记录与修订，不依赖暂停中的 Lua 协程栈恢复。

### 5.1 步骤与输入映射

| 候选构造器 | 做什么 | 进入下一步的条件 |
| --- | --- | --- |
| `ruleStep(ruleId, options)` | 根据 `options.input(state)` 生成规则输入，按流程固定修订调用规则 | 规则结果、效果和当前步骤完成记录原子提交后，按 `next` 转移 |
| `approvalStep(options)` | 给指定获准角色创建裁定待办，按 `responseSchema` 验证回应 | 获准裁定者回应并留痕；没有回应则持续等待或取消 |
| `inputStep(options)` | 给 `assignee(state)` 指定的参与者创建输入待办 | 接收合法回应，或进入唯一胜出的超时分支 |
| `endStep(options)` | 结束流程；可由 `options.result(state)` 返回汇总结果 | 结束记录已提交，不再接受该流程的新回应 |

`next` 可为步骤名或普通 Lua 函数；函数只能选择已登记步骤，不做业务写入。原分析中的 `effectStep` 仍可另行评估，本组采用“规则步骤提交效果”形态，避免作者在不同步骤手工重复应用同一提案。暂不混用自动提交和延后手动提交两种模式。

传给映射/分支函数的 `state` 是宿主生成的只读业务快照：

```lua
state.input                         -- 创建流程时已校验的输入
state.steps.check.result.passed     -- check 已成功完成后的结构化规则结果
state.steps.ruling.response.approved -- ruling 已提交的人工回应
```

`state.steps` 中只有已完成的步骤有结果；不能在上游分支读取尚未执行的后续步骤。流转前宿主保存当前步骤、规则/流程修订和依赖锁。规则业务拒绝或异常默认进入可诊断的失败状态，不把缺失结果当作 false 偷偷继续；首轮样例不自定义错误捕获分支。

01 和 02 的 `ruleStep` 每次执行均重新读取当前合法数据，进入等待前不预扣 HP。等待后若对象变化，宿主基于新读集校验；已声明的行动参数如需更改，则取消或重新确认该行动，不让裁定回应偷偷改成另一个目标。

### 5.2 身份、恢复与时间

`role = "keeper"` 表示谁可以回应，不表示后续任意步骤自动以 KP 身份执行。05 中后果作用于原调用者控制的同一角色；流程激活与调用权限必须允许这些既定效果，否则即使有人点了批准也应拒绝。未来若需审批授予额外能力，应另设计绑定具体对象、参数和有效期的授权凭据。

`inputStep.timeout.seconds` 从宿主首次持久化该待办时计算，保存绝对 UTC 截止时间；断线、重试或重启不重新倒计时。回应在截止前由权威端接受才有效，到期回应拒绝。回应与超时任务竞争同一待办版本，只有一条转换可提交。

07 的 `overdue = "executeOnce"` 表示停机错过截止后，恢复时补执行一次超时分支；无常驻后端时不承诺停机期间准点触发。06 的 `clock.round + rounds` 表示该逻辑时钟相应轮次的 `round.start` 边界，不能直接推广成某角色的“行动三次”或真实三分钟。时钟推进和状态到期需要原子记录/幂等回执。

## 6. 样例输入、预期与边界

以下均为独立场景，运行每行前恢复基线，避免把前一行的 HP 或数量变化误算进下一行。

基线为 `actor-001`：`example.skills.spotHidden = 60`、`example.resources.hp = { current = 9, max = 12 }`、`example.defense.armor = 2`。背包 `bag-b` 的 `demo.inventory.capacityMassG = 1000`；时钟 `combat-001.round = 5`。相关组件 schema 保证数值有限、HP 非负、护甲非负，技能范围为 0—100。所有 ID 均为自制测试数据。

| 样例 | 输入与受控条件 | 预期 |
| --- | --- | --- |
| 01 | `{actorId="actor-001", skillId="spotHidden"}`，固定骰面 25 | 目标 60、成功、无效果；固定骰面 85 则失败 |
| 02 | `{actorId="actor-001", rawDamage=7}` | 减伤后 5，HP 从 9 到 4；提案前快照仍为 9；伤害 100 时 HP 最低为 0 |
| 03 | `{itemId="item-001", fromContainerId="bag-a", toContainerId="bag-b", quantity=1}`；汇总 800g | 提出转移一个单位；汇总 1200g 时 `CAPACITY_EXCEEDED`，没有效果 |
| 04 | `{actorId="actor-001", skillId="spotHidden", environment="storm"}`，固定骰面 45 | 修正 20，目标 40，失败；未声明的环境返回业务拒绝 |
| 05 | `{actorId="actor-001", skillId="spotHidden", rawDamage=7}`，骰面 85 | 等待 KP；同意并附原因后调用 02，HP 到 4；拒绝则 HP 保持 9；骰面 25 则直接结束 |
| 06 | `{actorId="actor-001", clockId="combat-001", sourceKey="item-lantern-001", rounds=3}` | 来源状态在第 8 轮开始边界到期；同来源再次施加按策略刷新，其他来源不受影响 |
| 07 | `{playerId="player-001"}` | 指定参与者选择 open/leave；没有及时回应则返回 timeout；迟到或重复回应不能再次推进 |
| 08 | `{templateId="template-bandage", toContainerId="bag-b", quantity=2, reason="完成准备"}` | 提出授予两个单位；新实例/合并结果由宿主回执给出，无权执行者不得提交 |
| 09 | 激活为当前场次的 `reference.apply-damage` 覆盖；输入与 02 相同 | 额外减伤 2，HP 从 9 到 6；撤销后新调用恢复 02，旧流程仍用原固定修订 |

04 的 JSON 文件由宿主验证：`schemaVersion` 为 1，`environments` 是环境名到对象的映射，每项只含 0—100 范围内的整数 `penalty`。缺件、字段错误或非法数据使候选发布失败，不能带着半个新配置激活。重复执行读取同一内容快照，不在每次重试时读取正在变化的外部文件。

## 7. 游玩中新增与覆盖的设计演示

以下是宿主应提供的操作过程，当前没有可执行 CLI 或已实现按钮，勿把文字当成现有命令。

### 7.1 临场增加一条规则

先只装入 01—03、05—08。KP 需要暴风雨修正时，将 04 与其 JSON 文件一起暂存，预览差异，选择新增规则并应用到本场。宿主校验、保存完整内容修订后原子激活，并通知动作目录变化；新面板通过输入 schema 展示环境输入。

此时旧检定流程不自动改用 04。新流程如果需要环境检定，应发布引用 04 的新流程修订，或在安全步骤边界显式迁移。禁止以替换 Lua 全局函数偷偷改变等待中的流程。

### 7.2 本场临时覆盖已有规则

把 09 作为 `reference.apply-damage` 的显式场次覆盖暂存，预览与 02 的差异。宿主要求有权限者确认覆盖关系、目标场次和生效时点；不可由 Lua 文件自行选择全战役权限。

激活后新操作固定覆盖修订。已开始并固定 02 的 05 流程继续使用 02；若希望它也受新护佑影响，需要明确迁移或重新确认。撤销覆盖只改变后续调用，已经提交的伤害不自动返还。原文件被移走时，已保存的源码/数据快照仍用于恢复。

### 7.3 发布失败如何表现

语法错误应指出文件与行号；依赖缺失、重名、未知效果、输入/数据 schema 不合法分别给出诊断。失败保留原活动注册表，不退出正在运行的房间。预览、激活、撤销分别留存修订和审计；不让文件监听事件直接触发业务写入。

| 单文件负担 | schema、元信息与逻辑放在一起，方便复制 | 让用户/Agent 添加一条技能或输入字段，记录重复内容与改动错误 |
| 流程写法 | Lua 表＋命名步骤＋短函数，显式输入映射 | 对照过程式写法的可读性；持久化语义必须保持可恢复 |
| 效果字段 | 使用可被内核识别的提案，不直接写库 | 与内核原语定稿并补齐正反例，避免相同操作出现多套字段 |
| 状态与时间 | 逻辑轮次和真实截止分开 | 确定时钟 schema、到期边界、刷新规则和故障恢复 |
| 规则与流程发布 | 文件定义与宿主激活范围分开 | 让作者完成新增、预览、覆盖、撤销，验证是否需要更直观的工具 |
| 数据转换 | schema 决定空表是列表或对象，不传函数/协程/userdata | 锁定 Lua 实现后验证数值范围、缺失值和结果转换 |

建议步骤：先评审 01/02/05 的最短路径 → 定稿最小宿主 API 与返回契约 → 制作测试场次和加载器 → 跑通 04/09 的动态发布 → 验证持久等待、轮次与实时时钟 → 收集制作者和 Agent 的独立使用反馈。
