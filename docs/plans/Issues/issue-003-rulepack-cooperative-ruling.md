## 现象与预期

《激光与情感》需要多人各自完成协助检定，主持人确认参与者与准备／专长，再关闭协助并执行主检定。还需要将相等骰关联到玩家提问和主持人的真实回答。

现行文档的 `ask` 只接收 KP 或发起人的布尔答案，流程图无环；没有已说明的多人答案收集、协助关联及消费契约。聊天室已支持文字、回复和分享普通行动卡片，但文字发言不能自动成为可信裁定；flow 的回执目前均不能直接分享为行动卡片，包含已完成的 flow；具体限制见下方工程评估回复。

期望工程责任者明确：现有接口如何安全表达上述协作；是否完全由配置包与客户端编排即可完成；若确有宿主缺口，再讨论最小扩展。不能直接据此认定需要增加通用内核功能。

4. 洞察可用已有文字及回复交流；若要求可恢复、可关闭的结构化待办，需要明确其权威数据来源，不能把消息文本视为授权。

## 候选处理与临时绕行

优先由工程责任者提供基于现有动作、回执与实体状态的安全用法，明确跨账号权限与幂等边界。确实无法满足时，再评估最小结构化提案／裁定或关联记录能力；配置包作者不直接编辑工程代码和契约。

临时可由 KP 在聊天中组织协助、人工核对骰单并确认主骰数，洞察使用回复关联。此方式适合验证玩法，不能宣称已经实现自动防重复、可恢复的多人协作流程。

### 2026-10-31：工程评估回复

已对照现行文档与实现核查。结论：接入边界问题成立，但目前没有足够依据认定必须修改宿主代码；先回复已确认限制和候选验证路径，不因此增加通用内核功能。本轮未执行多人集成复现，不能以静态核查代替验收，也不关闭问题。

**现有能力与限制**

- 各玩家可以独立调用规则动作，复用主机随机、持久回执及同 commandId 重试；协助如何加骰、准备／专长是否成立仍由配置包及 KP 负责。
- `ask` / `flow.respond` 只接受 KP 或发起人的布尔答案，后续阶段仍按原发起者身份执行。KP 批准不会赋予跨账号写权限。现有流程不能直接充当多人结构化答案收集器。
- 命令幂等不等于业务防重复。同 commandId 重发不会重掷，但换 commandId 可能再次执行；需要持久维护“本次行动、参与者、是否提交、是否消费”的业务状态。
- Lua 现有 `r.set` 只修改有控制权实体的已有普通数值字段；没有通用业务记录写入或跨账号回执查询原语。`progress.set` 虽可保存结构化值，但属于 KP 管理命令，不能直接视作可由玩家规则原子更新的协作接口。
- 文字、私聊和回复可以承载洞察问答；消息文本本身不能成为规则批准或消费依据。“待回答／已回答／已关闭”等可恢复的结构化状态仍需另行定义。
- `chat.message.share` 仅支持本人已提交、公开且非 KP 专用的普通 action，并检查读取对象的可见性；已完成 flow 也不能直接分享。行动提交与卡片分享是两个事务，分享失败不撤销行动；再次分享同一行动也不能再次计入协助。

### 2026-10-31：配置包侧最小验证反馈

已按上述工程回复继续，用独立存档和真实宿主 HTTP 完成 27 项检查，全部通过。见[验证说明](../../../rulepacks/lasers-and-feelings/docs/history/2026-10-31-cooperation-validation.md)、[可复跑驱动](../../../rulepacks/lasers-and-feelings/tests/verify_cooperation.py)及[机器摘要](../../../rulepacks/lasers-and-feelings/tests/cooperation-results.json)。工程实现与其运行存档未修改。

验证覆盖：相同 ID 重试、不同 ID 重复协助、关闭与迟到、并发主检定唯一提交、消费防重复、分享失败与重复分享不影响业务、重启保留回执与骰值、撤权后拒绝已排队命令，以及文字回复和私聊受众。KP 在实验中兼任第二协助者，未验收三个普通玩家独立操作；洞察问答只有文字关联，没有结构化待办状态。

结论：固定参与者、单个行动的受限方案可由已有实体数值与普通 action 实现，无需为这个最小样例修改宿主。绑定数据固定于规则修订，每个行动仍需准备新记录与绑定，不能把样例通过等同于低成本作者工具已经可用。下一步优先评估现有关系或配置能否支撑可重复使用的绑定；再由工程责任者评估是否需要更小、更直观的通用接口。
