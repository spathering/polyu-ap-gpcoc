# 文档维护标准

- 文档类型：通用标准
- 状态：有效
- 创建日期：2026-10-29
- 最后更新：2026-10-29
- 关联文档：[文档索引](../README.md)

## 1. 适用范围

本标准适用于项目内维护的 Markdown 文档，包括根目录说明、分类索引、需求、调研、设计、操作说明和规范。文档默认使用中文、UTF-8 编码；路径、代码标识和专有名词可保留原文。

文档应反映可核实的信息，明确区分事实、推测、候选方案与待办。文档与实现不一致时，先核查实际行为并修正文档或实现，不以过期描述代替核查。

## 2. 分类与唯一来源

| 类型 | 目录 | 收录规则 |
| --- | --- | --- |
| 历史 | `docs/history/` | 已失效、被替代、取消或完成归档的记录 |
| 当前：设计 | `docs/current/design/` | 当前有效的目标、设计、约束与决策理由 |
| 当前：工程 | `docs/current/engineering/` | 与当前代码、配置及实际文件一致的工程说明 |
| 计划 | `docs/plans/` | 尚待讨论、验证或实施的内容 |
| 通用标准 | `docs/standards/` | 已生效且跨阶段适用的规则与约定 |

同一主题的有效正文只维护一份，其他位置通过链接引用。当前文档可以链接相关计划，但必须明确它尚未实现；历史材料必须链接后续有效文档（如有）。

`docs/current/README.md` 只作为当前文档入口；主题文档按设计或工程归类。工程内容必须与当前代码对齐，不保留已废弃实现作为现行说明。`docs/current/engineering/hierarchy.md` 是实际文件结构和施工占用登记的统一入口，不将计划新增路径提前写成已存在文件。

若文档之间出现冲突，先核实实现和最近确认的决策，再同步修正相关文档；不得仅凭文件位置或修改时间认定某一说法正确。

## 3. 命名与索引

- 各分类使用 `README.md` 作为入口，登记文档链接和简要说明。
- 主题文件采用简短、稳定的英文小写连字符名称，例如 `session-management.md`；正文标题使用清晰的中文名称。
- 历史文件采用 `YYYY-MM-DD-原文件名.md`，日期为归档日期；同日重名追加 `-02` 等序号。
- 不使用 `final`、`new`、`最新版` 等容易过期的名称，不通过复制多个“最终版”维护有效正文。
- 使用相对路径引用项目内文件。新增、改名、移动、删除文档时，同步维护所在分类索引及所有受影响的引用；分类结构变化时同步维护根目录和 `docs/README.md`。

## 4. 元信息与状态

除根目录说明、`AGENTS.md` 和各级索引外，主题文档应在标题下包含以下信息：

```markdown
# 文档标题

- 文档类型：当前 / 计划 / 历史 / 通用标准（选择一项）
- 状态：有效（按下表选择）
- 创建日期：YYYY-MM-DD
- 最后更新：YYYY-MM-DD
- 关联文档：相关文档链接；没有则写“无”
```

当前主题文档还应注明“文档子类：设计”或“文档子类：工程”。hierarchy 额外记录最近目录核对日期；占用登记的时间应包含时区。

| 类型 | 允许状态 | 含义 |
| --- | --- | --- |
| 当前、通用标准 | 有效 | 已确认且仍适用 |
| 计划 | 草案、待确认、已接受、进行中 | 从初步想法到执行中；已接受仍不等于已落地 |
| 历史 | 已归档 | 原文已结束或不再作为有效依据 |

按实际情况更新计划状态，不要求机械经过全部状态。确认方式按项目实际协作进行，尚无证据时不标记为“已接受”。

计划至少包含目标、范围、待确认问题、实施步骤与验收条件；调研材料应附来源及查阅日期，标明结论的适用条件。

更新正文时更新“最后更新”；仅修正排版、错别字或链接可不更新日期。重大决策应简要记录日期、结论、理由及替代关系，无需为普通文字修改建立冗长日志。

## 5. 同步维护流程

1. 修改前检查相关当前文档、计划和标准，确定本次变更影响的范围；按第 8 节先检查 hierarchy 并登记施工 ID 与占用范围。
2. 功能、接口、配置、架构或操作流程发生变化时，在同一变更中更新相应文档；示例与命令应符合实际环境。
3. 新增内容按用途放入对应目录，补充元信息与索引。暂未确认或未落地的内容写入计划，不写成现有能力。
4. 计划部分完成时，分别写清已落地内容和剩余事项；只有已验证的结论进入当前文档或标准。
5. 计划完成、取消或被替代时，将有效结论整理到对应文档，再归档原计划。有效文档或标准被替代时，保留必要背景并归档旧文档。
6. 提交或交付前检查链接、分类、状态、日期，以及事实与实现是否一致。纯文档变更无需运行无关的代码测试；涉及操作说明或示例时应在可用环境中验证，无法验证则明确标注。
7. 增删、移动或重命名文件时，同步更新 hierarchy 的实际目录清单和最近目录核对日期，修正相关引用。
8. 每次阶段更新（阶段交付、里程碑完成或集中同步工程状态）必须核对全部工程文档与当前代码、配置和目录，剔除已废弃的功能描述、路径、接口、配置与命令。有追溯价值的旧内容移入历史目录，只保留指向历史的必要链接，不在有效正文保留失效说明；日常变更同样及时更新。
9. 完成核对与交付准备后释放自己的施工登记；取消、交接或结束工作时也必须释放，不留下无人维护的占用。

与文档无关的变更无需产生形式化的文档修改。

## 6. 归档要求

归档时在原文顶部记录以下信息，正文保留有价值的原始背景：

```markdown
- 文档类型：历史
- 状态：已归档
- 创建日期：原创建日期
- 最后更新：YYYY-MM-DD
- 原路径：docs/plans/example.md
- 原状态：进行中
- 归档日期：YYYY-MM-DD
- 归档原因：完成 / 取消 / 被替代，以及简要说明
- 替代文档：后续有效文档链接；没有则写“无”
- 关联文档：其他相关链接；没有则写“无”
```

归档采用移动方式，避免在有效目录留下失效正文。同步更新原分类索引、历史索引及引用链接；指向旧文件的引用应按语义改为历史记录或后续有效文档。

历史文档只在纠错、补充替代关系或修复链接时修改，并增加注明日期的修订说明。无价值的临时草稿可删除，但需清理引用；有决策背景的内容应保留归档。

## 7. 交付检查

- [ ] 分类与状态准确，未将计划写为已实现事实。
- [ ] 主题文档元信息齐全，日期符合实际。
- [ ] 所在分类索引已登记，内部链接能解析到目标。
- [ ] 受影响的说明、示例和操作步骤已同步更新。
- [ ] 被替代内容已归档，并写明原因与后续入口。
- [ ] 工程文档与当前代码、配置及文件一致；阶段更新已清理废弃内容。
- [ ] hierarchy 清单与实际目录一致，自己的施工登记已释放或按规则交接。
- [ ] 未包含密码、令牌、私密会话内容或其他不应入库的信息。

本标准发生变化时，同步检查相关索引和 `AGENTS.md`；旧标准有追溯价值时按本标准归档。

## 8. 施工占用与冲突处理

### 登记内容

Agent 和相关人员在施工前，必须检查 [hierarchy](../current/engineering/hierarchy.md) 并登记，文档修改也属于施工。单纯首次读取该文件和规则以完成登记无需提前占用。

每条记录包含：唯一 ID、相对项目根目录的路径范围、使用方式、任务、开始时间和最后确认时间（使用带时区的时间，如 `2026-10-29T12:00:00+08:00`）。ID 使用可辨识的 Agent/人员标识加会话或任务唯一后缀；同一人或 Agent 的并行任务使用不同 ID。

| 方式 | 含义 | 冲突规则 |
| --- | --- | --- |
| 使用 | 依赖文件内容保持稳定的阅读、分析或运行，不修改该范围 | 允许多个“使用”并存；与重叠范围的“改动”互斥 |
| 改动 | 编辑、创建、删除、移动、重命名或可能写入文件的操作 | 与重叠范围的任何占用互斥 |

路径使用 `/`，目录以 `/` 结尾并覆盖全部子路径；`.` 表示整个工程，只在确实需要全局施工时使用。Windows 路径比较不区分大小写，应统一为项目内规范路径。相同路径或父子范围均视为重叠；移动、重命名必须同时登记源与目标范围。新增文件先在占用表登记拟新增路径，文件创建后再加入实际清单。构建、测试等会写入文件的操作也应覆盖其输出范围。

### 施工步骤

1. **检查**：读取最新 hierarchy 和实际文件，确认所需范围没有冲突。遇到冲突则等待，或先与占用者协调缩小、拆分范围，不直接开始冲突部分的工作。
2. **登记**：保留他人记录，添加自己的 ID 和使用/改动范围；写入后重新读取，确认自己的登记存在且没有重叠冲突，再开始施工。
3. **维护**：范围扩大、由使用转为改动或产生额外写入前，先重新检查并补登记。任务仍在进行时，在恢复施工、阶段更新和交接前刷新最后确认时间。目录变化同步实际清单。
4. **释放**：完成必要核对、取消或交接时删除自己的活动记录，保留其他 ID 的记录。活动表不承担历史日志用途，需要保留的结果写入相关文档。交接时先协调由谁接手，原 ID 释放后由接手者登记并复核，禁止直接沿用他人 ID。

### 登记表自身与异常情况

登记表是共享协调入口。只为登记、刷新或释放自己记录的元数据编辑，不要求先占用 hierarchy 自身，以免递归；修改其目录正文或规则仍需登记改动范围。已有施工者也不得阻止其他人安全登记不冲突范围。

每次写登记表前重新读取最新版本，只改自己的行，保留他人记录。发现文件在编辑期间被其他人更新时，基于最新版本合并并重新复核，不用旧副本覆盖。若多人同时登记造成记录丢失或冲突，相关施工先停下，串行协调登记，确认一致后再恢复。

这是协作登记机制，Markdown 表本身不提供原子文件锁；不能保证未遵守约定的进程不会写入。出现同时抢占或无法确认状态时，应由参与者指定一位协调者串行处理，不凭“已写入自己的 ID”认定获得独占。

异常中断留下的记录不按时间自动过期，不得仅因记录较旧而删除。恢复施工时先确认会话与工作是否仍有效，再刷新或释放自己的记录；他人遗留记录必须联系占用者或由项目负责人确认原工作已停止后才能清理，并在任务交接记录或相关文档中注明清理依据。活动记录不得随历史归档一并搬走，先完成释放或交接。
